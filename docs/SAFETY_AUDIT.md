## 结论

**被审计版本暂不应直接用于主存档。** 未发现直接删除或覆盖存档文件、改写存档二进制格式、引入自定义可保存 ECS 组件的代码，也未复现存档损坏或无法读取。
但加载后的线路缓存校正、共享数据还原和部分失败处理存在防护缺口，可能留下不一致的模拟状态，并被后续保存。
“没有自定义保存格式”“没有 Harmony”以及数学测试通过，都不能证明存档安全。

P1 表示使用主存档前必须解决并验证的优先项；P2 表示应补齐的边界或兼容性防护。
优先级不表示已经发生不可逆坏档。下文分别说明代码事实和仍待复现的影响。

## 已核实的数据路径

| 数据 | 本机程序集证据 | 安全含义 |
|---|---|---|
| `Game.Policies.Policy` | 实现 `ISerializable`，保存 policy 引用、flags、adjustment；读取 adjustment 时不做 clamp | 超出原始范围的逐线路设置可被保存 |
| `Game.Routes.RouteModifier` | 实现 `ISerializable`，保存并读取 `m_Delta(float2)` | 本 mod 直接改写的线路效果缓存具有保存路径，不能笼统称为“只改 prefab” |
| `PolicySliderData` / `RouteModifierData` | 类型本身不实现 `ISerializable` | 不能据此推论线路缓存不保存 |
| `TransportDepotData` | 实现 `ISerializable`，容量按 int 保存；`Combine` 使用普通 int 加法 | 尚未闭合每类 prefab / 合并数据实际落盘范围的证明，不能断言所有被改容量一定保存 |
| `Buildings.TransportDepot.m_AvailableVehicles` | byte；原版写入前 `math.clamp(value, 0, 255)` | “超过 255 自动发生字节回绕”不是本次确认的问题 |

原版 `GetModifierDelta` 对归一化输入执行 `saturate` 后再 `lerp`。
但重新换算时的钳制，不能证明从存档读回的旧缓存已经被重新计算。

原版缓存刷新调用见于策略修改事件和 `RouteModifierInitializeSystem`；后者查询 `Created + Route + Policy`，排除 `Temp`。
本次未闭合正常加载是否对每条既有线路重新赋予 `Created` 的全链路证明，不能假设全部自动刷新，也不能断言绝不刷新。

## F1：加载后的线路缓存缺少独立核验（P1）

位置：[LineCeilingSystem.cs](../Systems/LineCeilingSystem.cs)，第 63、123、161、169、198、210 行。

**代码事实，置信度高：** 加载回调仅设置 pending；关闭功能或倍率为 1 时进入 `RestoreNow`；只有 prefab 范围变化才触发刷新，刷新又仅处理超过共同上限的目标 policy。

风险场景：存档保存过扩展状态下的 `RouteModifier`，重新加载时 prefab 已是原始范围、设置关闭或倍率为 1，`changed=false` 使本 mod 跳过校验。
如果原版该加载路径未重建缓存，就可能继续使用旧效果并再次保存。
同一 World 切换存档时，也不能由“范围没变”推论“新载入缓存正确”。

**漏核验分支确定存在；实际触发范围和持久影响尚未在游戏中复现。**

整改：将加载后的一致性核验与范围变化后的增量刷新分开；在 policy、范围和写入归属验证后，对正式线路按当前政策核验或校正 `VehicleInterval`，保留其他槽位。
还需准备卸载流程及有 / 无 mod 往返测试；移除 mod 后它无法再执行清理。

纯逻辑示例（不是游戏实测基线）：slider `50..200`、modifier `-0.5..1` 扩展到 sliderMax `1000`、modifierMax `9` 后，adjustment `800` 的逆相对效果为 `-0.875`；原始范围下重新计算为 `-0.5`。
只恢复范围而未校正旧缓存时，两种状态并不相同。

## F2：重新应用和还原缺少写入归属检查（P1）

位置：[LineCeilingSystem.cs](../Systems/LineCeilingSystem.cs)，第 152、185 行；[DepotCapacitySystem.cs](../Systems/DepotCapacitySystem.cs)，第 101、127 行。

**代码事实，置信度高：** 仅保存首次快照，不记录最后写入值；重新应用使用旧基线，还原直接写回旧范围或旧容量。

原版 `TransportDepotMode.ApplyModeData` 和 `RestoreDefaultData` 确实存在修改同一车库容量字段的路径，不能假设该字段永远只由本 mod 改写。
当前城市是否触发这些模式尚未验证。

示例：初值 20，本 mod 写 100，其他合法系统随后写 60；当前还原会写 20，重新应用可能写 100，均未识别 60 的来源。这些数字只是分支说明。

整改：记录最后应用值，仅在当前受管字段仍等于本 mod 最后写入值时还原；外部变化应停止覆盖并记录冲突。
需要继续兼容原版模式切换时，应设计明确的协调 / 重取基线机制，避免把已放大的值重新当作基线。

## F3：部分失败可能留下混合状态且不再重试（P2）

位置：[LineCeilingSystem.cs](../Systems/LineCeilingSystem.cs)，第 70、154、198 行；[DepotCapacitySystem.cs](../Systems/DepotCapacitySystem.cs)，第 65、94、127 行；[Mod.cs](../Mod.cs)，第 35 行。

**代码事实，置信度高：** 应用前清除 pending，随后跨组件和实体顺序写入；异常只记日志，没有完整回滚，pending 也不会因该异常自动恢复。
还原方法同样吞下异常，调用方无法判断是否完整成功。

中途异常可能使范围、modifier、部分线路或车库处于不同更新阶段；随后保存可能保留当时模拟状态。本次未复现该异常。

整改：预检并计算修改计划，记录已写条目；失败时只回滚仍属于本 mod 的写入，明确失败状态，并采用有限重试或安全停止策略。
必须提供可检查的还原结果，不能以“调用过还原方法”代替“还原成功”。

## F4：容量零值和后续计算边界未完整处理（P2）

位置：[DepotCapacitySystem.cs](../Systems/DepotCapacitySystem.cs)，第 108 行。

**代码事实，置信度高：** `Math.Max(1, original * multiplier)` 会把零值或负基线变为 1。
long 中间值避免本 mod 的乘法溢出，但 `int.MaxValue` 只是类型上限；原版后续合并容量使用普通 int 加法。

尚未证明当前资产具有零 / 负哨兵容量或接近溢出范围。
整改应跳过并告警不支持的基线，核对升级和合并语义；不能仅靠夹到 int 上限，也不能凭 byte 字段推断所有容量必须限制为 255。

## F5：线路查询边界偏宽（P2）

位置：[LineCeilingSystem.cs](../Systems/LineCeilingSystem.cs)，第 59、214 行。

**代码事实，置信度高：** 仅要求 `Policy` 与 `RouteModifier`，未要求 `Route`，也未明确排除 `Temp`、`Deleted`。
只要相关实体满足查询及高 adjustment 条件，就可能被处理；本次没有运行时实体集合证明实际误写。

整改：收窄到目标正式线路，排除临时和删除标记，加入线路编辑、撤销和删除回归。

## F6：“客运车库”筛选不区分客货用途（P2）

位置：[DepotCapacitySystem.cs](../Systems/DepotCapacitySystem.cs)，第 144 行。

**代码事实，置信度高：** 白名单仅按交通类型筛选；火车、船和飞机的交通类型不足以证明设施仅客运。
尚未证明某个货运资产实际携带目标组件或已被误改。

整改：依据实际 prefab 用途和组件明确筛选，覆盖升级组件；文档中的功能范围必须与实际处理集合一致。

**整改结果（2026-11-26，推翻上面「仅客运」的严格实现）**

第一版按字面把「仅客运」实现成 `purpose == DepotPurpose.Passenger` 的严格相等。实际游戏中 34 个候选 prefab **全部被跳过**，地铁与公交车库都没有扩容，而设置面板仍显示「已应用」——这是一次静默失效，比筛选偏宽更难发现。

改为「**至少一条客运线路或客运站组件到达，且没有任何货运用途到达**」（`(purpose & Passenger) != 0 && (purpose & Cargo) == 0`）后实测：

```
[车库完成] multiplier=10; candidates=34; eligible=6; changes=6; skipped=28; conflicts=0
[车库筛选] 无法解析=0; 类型不支持=24; 含货运或无客运=4; 容量非正=0
```

- `Unknown`（用途未证）与 `RepeatableUpgrade`（可重复容量升级）不再一票否决：两者都不能证明设施属于客货共用。
- 类型白名单仍是第一道闸，24 个 `Outside Connection` / `Taxi` / 货运场站照旧跳过。
- 仍在跳过范围：与货运共用 `TransportType` 的火车场站（实测 `RailYard02`，`Train` 同时被货运线路使用且不是 `TransportStation` prefab，拿不到 `Passenger` 位）。若要覆盖，需要为铁路单独设判据，不能放宽为「按类型放行」。

## 默认行为

[Setting.cs](../Setting.cs) 第 14–17、74–79 行默认开启两项功能、倍率均为 5。
首次加载即扩大所有匹配车库容量，但**不会把所有线路当前配车数直接乘 5**。
对于未通过安全验收的版本，建议改为默认关闭或 1 倍，由用户明确启用。

## 定向兼容性结论

静态扫描未发现另一个已检查的托管 mod 直接改写同一组配车 policy 范围；不能据此保证所有组合安全。
以下仅列与本功能相关的交互类别，不是本机完整 mod 清单。

| 功能类别 / 代表 mod | 已核实的交互 | 需要验证 |
|---|---|---|
| 分区派车 / Traffic Tool Essentials | 在原版车库 AI 前筛选车库和处理派车请求，统计读取容量 | 分区内外派车、容量变化、减车后的请求清理 |
| 手动驾驶 / CSL Driving Life: Bus Driver | KeepOnLineJob 写车辆状态以保持驾驶中的车在线 | 驾驶中减车、停线、准备卸载 |
| 多节车辆 / Articulated Buses | 拖车生成、恢复与清理 | 多节车辆统计、回库和重载 |
| 航空调度 / Realistic Aviation | 读取公共交通状态，存在地面延误和 hold 路径 | 高飞机数量、滑行排队、保存与重载 |
| 交通模拟 / Traffic | 未发现同一配车范围的直接写入 | 更多车辆造成的寻路、拥堵和模拟负荷 |
| UI、停车、车站、路径、绘制类扩展 | 未发现直接改写同一组核心字段的明确实现 | 原版滑块显示、路径行为、车辆增加后的处理负荷 |

这些是条件性功能交互或性能风险，不是已确认的坏档冲突。
程序集 / UI 出现 `VehicleCountSection` 名称不等于覆盖滑块；停车 policy 不等于公交线路 policy；名称含 Line 的摆物工具不应被误认作公交管理器。
新增配车上限、时刻表、直接写 `VehicleInterval` 或车库容量的 mod 时，应重新审查。
